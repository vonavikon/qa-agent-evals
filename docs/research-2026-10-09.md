# Open sources: what to borrow into the architecture (2026-10-09)

Question: are there methods and modules to improve the qa-agent-evals architecture. Short answer: few ready modules fit embedding (we are a Claude Code plugin, not a python package). Four ideas from mature frameworks are worth borrowing. Sources were alive as of October 2026.

## What the review showed

**Three framework leaders** ([DeepEval comparison](https://deepeval.com/blog/top-5-llm-evaluation-frameworks), [benchlm guide](https://benchlm.ai/llm-evaluation-frameworks)) differ by the layer where evaluation lives: Promptfoo is configuration with assertion checks and no judge (cheap, deterministic). DeepEval is pytest style with 50+ metrics and an LLM judge. Inspect AI (UK AISI) is a Task = Dataset + Solver + Scorer architecture with reducers and a recomputable log. Our pipeline is a fourth variant (agentic orchestration inside Claude Code itself), closest to Inspect by structure.

**Tracing is converging on a standard**: OpenTelemetry GenAI semantic conventions ([overview](https://opentelemetry.io/blog/2026/genai-observability), [agent semantics](https://opentelemetry.io/blog/2025/ai-agent-observability)) define a "run = trace, calls = spans, tokens = metrics" model. Langfuse is a popular OTLP backend ([integration](https://langfuse.com/integrations/native/opentelemetry), [agent evaluation over traces](https://langfuse.com/resources/engineering/ai-agent-evaluation)). The replay technique re-scores changes over recorded traces without new runs ([Kerno on reproducibility](https://www.kerno.io/blog/improving-trace-visibility-and-reproducibility-in-langfuse), [ZenML comparison](https://www.zenml.io/blog/opik-vs-langfuse)).

**Inspect details** ([scorers](https://inspect.aisi.org.uk/scorers.html), [multiple scorers + reducers](https://inspect.aisi.org.uk/multiple-scorers.html), [metrics](https://inspect.aisi.org.uk/metrics.html)): a scorer is a first-class interface (deterministic / model-graded). The reducers `majority`, `at_least(k)`, `passk` aggregate repeats. The `.eval` log (JSON) lets you recompute verdicts without new runs (with caveats, [issue #5612](https://github.com/UKGovernmentBEIS/inspect_ai/issues/5612)).

## What we borrow (priority order)

1. **A machine-readable run log (after the Inspect .eval pattern).** Today the artifacts are markdown and code cannot reuse them. Add `runs/<дата>-<sut>/index.jsonl`: one line per run (id, type, feature, repeat verdicts, reducer result, paths to txt/prov/diag/verdict, judge model). This opens re-scoring (re-judging without runs, so our v1 re-judge would become a command), summaries, and script-driven comparison of acceptance runs. Cheap, maximum use.
2. **An explicit reducer for repeats (Inspect).** Replace the hand-written PASS-rate with named reducers in oracle.md. `majority(N)` is the majority outcome (our default at N=2 is unanimity or a flag). `at_least(k)` serves critical cards, `passk` measures defect frequency. The formalization removes the ambiguity of «GOT 1/2».
3. **A scorer interface in the architecture (Inspect).** Name the layers explicitly: deterministic-scorer (grep facts, already there), model-graded-scorer (judge step 1), supervisor-scorer (judge step 2), reducer (repeat aggregation). This renames what exists. Still, it gives a language and an extension point (a new scorer = a new check type with no pipeline rework).
4. **Provenance as a trace (OTel idea).** Our events.jsonl + prov.txt is an embryo of a GenAI trace. Keep the fields (who called, what was read, how many tokens) semantically compatible with the span model, so an export to OTLP/Langfuse needs no rework.

## What we do NOT take

- Embedding the libraries themselves (DeepEval/promptfoo/Inspect): a different runtime (python vs a Claude Code plugin). Our pipeline is agentic, theirs is programmatic.
- Langfuse CI gates and dashboards: overload for a pet project. The JSONL index covers the need.
- Full-dialog dataset replay: stateless moves already give isolation. Re-scoring over protocols closes the scenario cheaper.
