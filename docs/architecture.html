qa-agent-evals · архитектура конвейера

Интерактивная схема: пять фаз приёмки, агенты, артефакты и инфраструктура. Кликни любой узел — справа его разбор: входы, выходы и рычаги влияния (какой файл или параметр это меняет).
агент гейт человека артефакт скрипт SUT
Инфраструктура прогона — обслуживает фазы D и E, кликни для деталей

Выбери узел схемы, чтобы увидеть разбор и рычаги влияния.

Проверка одной карточки разложена на четыре именованных слоя (заимствовано из Inspect AI). Новый тип проверки = новый scorer, конвейер не переделывается. Сверху вниз сигнал слабеет; где возможна проверка уровнем выше — поднимай её туда.

1 · deterministic-scorer

программная часть судьи · grep по транскрипту

Матчинг facts_must / facts_must_not по тексту ответа и провенансу. Без мнения модели: факт либо дословно доказан цитатой/прочитанным файлом, либо нет.

2 · model-graded-scorer

судья, шаг 1 · LLM на другой модели

Смысловая оценка по оракулу. Вход изолирован: оракул + протокол, без persona и instruction — судья не знает замысла карточки. Шкала GOT / HONEST / PARTIAL / FAIL / ATTACK_PASSED.

3 · supervisor-scorer

судья, шаг 2

Супервизия исполнителя: держал ли роль, не помогал ли SUT, дожал ли сценарий. INVALID — только по явным критериям, не по вкусу.

4 · reducer

оркестратор · агрегация повторов

majority (дефолт) / unanimous / at_least(k). Расхождение повторов = split — пограничное поведение, решение за человеком. Комитеты смягчают шум, но не коррелированные смещения судьи.

Плановое усиление (research-rsi, P1): факты, которые можно проверить grep'ом, уводятся из LLM-судьи в слой 1 — исполнимая проверка сильнее мнения модели.

Вся настройка конвейера — правками этих файлов. Колонка «когда» подсказывает момент, где рычаг обычно двигают.

Подход

Приёмочное тестирование зондами: не «прогнали промпты и посмотрели», а заранее записанный оракул против каждой карточки, судья на другой модели, изолированная среда и асимметричные выводы. Критерий оценки скрыт от тестируемой системы (развязка публичного и приватного сигнала, arXiv:2609.26457).

Асимметрия вердиктов

FAIL / ATTACK_PASSED — доказательство дефекта. Позитив — «не опровергнуто за N прогонов» (risk bounding), не «доказано». Формулировка «система прошла приёмку» запрещена.

Оракул до прогона

Ожидания и факты фиксируются до диалога и не правятся после — вердикт не подгоняется. Факты бинарны (facts_must / facts_must_not), не градуированы.

Изоляция по иерархии

Исполнители не знают друг о друге; судья не знает замысла карточки на шаге 1; SUT-сессия не видит среду владельца (нейтральный cwd, без скиллов и MCP).

Судья на другой модели

Генератор и оценщик в одной сущности реплицируют свои смещения (arXiv:2607.07663). Разводка: headless-вызов с явной --model, выбор согласуется с человеком в фазе B.

Повторы и редьюсеры

N прогонов на карточку (дефолт 2; расхождение — сигнал поднять до 5 на critical/adversarial). Шум — главная угроза валидности, усреднение обязательно.

Корень каждого негативного вердикта

FAIL / PARTIAL / ATTACK_PASSED получают разбор: сломала система, сорвал исполнитель или ошибочен оракул. Маркер доказывает выдачу, не секретность выданного.

Субагенты по потребности

Оркестратор и аналитик порождают помощников под задачу: бюджет фазы общий, каждый зафиксирован в артефакте (кто, зачем, что читал). Исполнитель и судья — нет: измерительная цепочка не расширяется.

Dev/test дисциплина

Фикс плагина, найденный самоприёмкой, закрыт только после контрольного прогона на внешней SUT — иначе overfitting на себе.

Плацебо-правило для циклов улучшения

После оптимизации харнесса (HALO-класс) валидация только свежими карточками; старый набор — регрессионный дым. Улучшение может следовать инструкции, а не доказательствам (+24 п.п. на плацебо, arXiv:2607.07663).
