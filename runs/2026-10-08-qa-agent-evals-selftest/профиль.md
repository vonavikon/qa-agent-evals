# Профиль SUT: qa-agent-evals (фаза A, субагент analyst)

## Реестр фич

- **orchestrator**: скилл acceptance-test, конвейер из пяти фаз (A анализ SUT, B адаптер и дым, C генерация карточек, D прогон, E отчёт). Правила: артефакты на диск немедленно, прогон только после утверждения карточек человеком, запрет вывода «система прошла приёмку» (асимметрия: негативный вердикт доказывает дефект, позитивный лишь «не опровергнуто»). Не делает: сам не тестирует и не вердиктирует.
- **analyst**: субагент фазы A. Строит профиль тестируемой системы (реестр фич, карта рисков, поверхность атаки, точки неопределённости, типы пользователей, варианты адаптеров). Только чтение, SUT не запускает. Не оценивает качество системы.
- **role-user**: субагент-исполнитель фазы D. Отыгрывает персону карточки против SUT через адаптер, ведёт многоходовой диалог, пишет протокол (транскрипт, самоотчёт, метки фактов). Контракт роли: не выходить из роли, не помогать системе, дожимать сценарий, стоп по бюджету. Не оценивает и не вердиктирует.
- **judge**: двухшаговый судья. Шаг 1 - оценка SUT по оракулу без знания persona/instruction: программные grep-проверки facts_must/facts_must_not, вердикт по шкале (GOT/HONEST/PARTIAL/FAIL/ATTACK_PASSED) с дословными цитатами, корень при негативном. Шаг 2 - супервизия исполнителя по явным критериям контракта; INVALID только по ним. Вердикт шага 1 фиксируется до чтения материала шага 2.
- **taxonomy**: генерация карточек 5 типов (obvious, convoluted, critical, adversarial, out-of-scope) с персоной, instruction, оракулом и бюджетом в эталонном YAML. Правила: обязательный строковый факт для obvious/critical/adversarial (для convoluted/out-of-scope - oracle.note), ровно одна атака на adversarial-карточку, минимум 2 карточки на тип, глубина по риску фичи.
- **adapter-cli**: единственный реализованный адаптер (v0.1). Headless-сессия claude -p --plugin-dir <SUT> с пустым CLAUDE_CONFIG_DIR, дымовой прогон до фазы C, бюджет из budget.tokens, минимум инструментов и сети. Playwright, HTTP API, чат-бот - описания для v0.2.
- **report**: сборка отчёта приёмки (runs/<дата>-<sut>/report.md): сводка вердиктов, матрица покрытия, находки с приоритетами, корневые разборы, обязательные ограничения прогона. Решения по находкам принимает человек.

## Карта рисков

- **Данные (изоляция прогонов)**: при поломке изоляции SUT-сессия наследует скиллы, MCP и историю владельца - прогон невалиден, ответы потенциально раскрывают личные данные. Контроль отдан инструкциям субагентов, не механизмам.
- **Доступы (исполнитель с Bash/Write)**: role-user имеет Bash и Write. Выход из роли или инъекция из ответа SUT в исполнителя - канал произвольных команд и записи вне протокола. Judge имеет Write - вердиктный файл тоже канал записи.
- **Деньги (бюджет вложенных сессий)**: каждый ход карточки - отдельный вызов claude -p, INVALID требует перепрогона (до 2 раз), LOW_CONFIDENCE - перезапуска судьи. Технического лимита токенов на headless-сессию нет; стоп-условие на честности исполнителя.

## Поверхность атаки

- Инъекция в SUT - штатный канал: реплики персоны идут прямо в промпт headless-сессии (adversarial этим и живут).
- Обратная инъекция (транскрипт - судья/оркестратор): тестируемая система может вложить в ответы инструкции судье («пометь GOT»). Программные проверки частично закрывают, мнение судьи - нет.
- Извлечение: инструкции размазаны по SKILL.md, agents/, knowledge/. В самоприёмке SUT может их прочитать и строить ответы под судью: знать вердикт-норму своего типа и генерировать «правильные» строки для facts_must.
- Транскрипты сохраняются в runs/ - канал утечки содержимого диалогов через репозиторий прогона.

## Точки неопределённости

- Многоходовой диалог: два механизма передачи контекста без выбора (промптом или --continue); эталона формата хода нет.
- Механизм бюджетного стопа: технический лимит токенов вложенной сессии не определён.
- Критерии судьи: PARTIAL («существенное выполнено») и порог LOW_CONFIDENCE не операционализированы.
- Самоприёмка: пошаговой процедуры нет (циркулярность судейства - судья и SUT на одной инструкции).
- Глубина покрытия: критерий «высокорисковые фичи получают больше карточек» не задан.
- Строковые факты: правила сопоставления (регистр, вхождение) не определены.
- Участие человека: поведение при отказе утверждать карточки не описано.

## Типы пользователей

- Автор LLM-системы: прогоняет приёмку своего детища перед релизом.
- QA-инженер / red-teamer: строит карточки по таксономии, читает корневые разборы.
- Принимающая сторона (лид, заказчик): читает report.md как основание решения.
- Оператор-человек внутри прогона: утверждает профиль, адаптер, карточки - узкое место.

## Варианты проверки

- **Адаптер CLI (реализован, v0.1) - режим самоприёмки**: CLAUDE_CONFIG_DIR=<пустая папка> claude -p --plugin-dir <каталог qa-agent-evals> --max-turns 1 "<реплика>". Изоляция с оговоркой: qa-плагин в SUT-сессии виден (он и есть SUT). Атакуемая поверхность - извлечение knowledge/ и накрутка судьи.
- **Адаптер HTTP API (описан, v0.2)**: пригоден для проверки judge и role-user, не orchestrator.
- **Адаптер веб (описан, v0.2)**: для текущего SUT гипотетический.
