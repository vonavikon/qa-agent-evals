 3  /// Expand a port spec like "8080,443,9000-9005" into the full port list.

14              ports.extend(lo..=hi);

17              ports.push(port);
18          }
19      }
20      Ok(ports)

### 1. No tests for input-shaped logic (`whole file`)
**Rule:** Logic with no tests (rust-review skill, "Documentation and tests"; M-TEST-INPUTS-style baseline — parse functions fed argv/config are exactly where edge cases live)
**Problem:** This function's whole job is dissecting untrusted strings, and every interesting behavior (range expansion, whitespace, inverted ranges, trailing commas, out-of-`u16` bounds) is untested. A future refactor of line 8's `split_once` branch could silently regress `"-1"` handling with nothing to catch it.
**Fix:**
```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn expands_mixed_spec() {
        assert_eq!(
            parse_ports("8080,443,9000-9005").unwrap(),
            [8080, 443, 9000, 9001, 9002, 9003, 9004, 9005]
        );
    }

    #[test]
    fn tolerates_whitespace() {
        // exercises both trims: outer per-element, inner around the dash
        assert_eq!(parse_ports(" 8080 , 9000 - 9001 ").unwrap(), [8080, 9000, 9001]);
    }

    #[test]
    fn rejects_bad_specs() {
        assert!(parse_ports("9000-8000").is_err()); // inverted range
        assert!(parse_ports("8080,").is_err());     // trailing comma
        assert!(parse_ports("99999").is_err());     // out of u16
        assert!(parse_ports("1-2-3").is_err());     // second dash
    }

    #[test]
    fn documents_surprises() {
        assert_eq!(parse_ports("+80").unwrap(), [80]); // u16 FromStr accepts '+'
        assert_eq!(parse_ports("0").unwrap(), [0]);    // port 0 allowed
    }
}
```
The last test deliberately pins the surprising behaviors — see finding 3.

### 3. `+80` and `0` are silently accepted (`parse_ports.rs:16`)
**Rule:** `impl FromStr for u16` accepts an optional leading `+` and leading zeros (std docs); port 0 means "OS-assigned" in `bind`, not "no ports"
**Problem:** A typo like `+80` parses as `80` with no signal, and port 0 in a bind context would surprise the user at runtime with a random port. Neither is *wrong* — but for a CLI this strict elsewhere (trailing comma errors), accepting them is inconsistent. Decide and pin it in the test from finding 1.
**Fix (if you want strict):**
```rust
let port: u16 = s.parse().with_context(|| format!("invalid port {s:?}"))?;
if port == 0 {
    bail!("port 0 is not allowed");
}
```
(For the `+`, either pre-validate `s.chars().all(|c| c.is_ascii_digit())` or accept and document it.)

### 4. Duplicates preserved; expansion unbounded (`parse_ports.rs:14`)
**Rule:** Design decision to confirm — bound work derived from input (not lint-enforced; citing the mechanics: each range contributes ≤ 65,536 items and the item count is unbounded by the function)
**Problem:** `"80,80-81"` yields `[80, 80, 81]` — harmless for listing, confusing if these feed bind attempts. And each range is ≤ 65,536 ports, so a spec with many ranges expands to spec-length × ~9,000 entries; fine for argv, worth a thought if this ever reads specs from a config file. Keeping spec order (no sort) is the right call, so `dedup` would need a `HashSet` pass or an ordered variant — possibly not worth it.
**Fix (only if specs may become large/hostile):**
```rust
if ports.len() + (hi as u32 - lo as u32 + 1) as usize > 100_000 {
    bail!("port spec expands past 100_000 ports");
}
```

### 5. No `# Errors` doc section (`parse_ports.rs:3`)
**Rule:** Document error cases — pedantic clippy enforces this as `missing_errors_doc` for `Result`-returning fns
**Problem:** There are three distinct failure modes (bad port, bad range bound, inverted range); a three-line `# Errors` section makes them discoverable.
**Fix:** add to the doc comment:
```rust
/// # Errors
/// Fails on a malformed port, a malformed range bound, or a start > end range.
```

### 6. Loop variable `s` shadowed and cryptic (`parse_ports.rs:7`)
**Rule:** Names should be descriptive; avoid single-letter names the reader must decode (Google Rust Style Guide, naming)
**Problem:** `let s = s.trim()` shadows with a name that says nothing, and `s` appears in six places. `part` says what it is. Pure readability, zero behavior change — happy to be overruled.
**Fix:**
```rust
for part in spec.split(',') {
    let part = part.trim();
```

- **Idiomatic anyhow.** `with_context(|| format!(...))` closures allocate only on the failure path; mixing `bail!` for the domain rule with `Context` for parse errors is consistent.
