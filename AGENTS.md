# AGENTS.md

Guidance for coding agents working in this repository.

## What this repo is

qa-agent-evals is a Claude Code plugin that runs acceptance testing for LLM systems
(a SUT, "system under test": plugins, skills, bots, browser apps). An analyst
subagent profiles the SUT, scenario cards are generated and approved by a human,
executor subagents play user roles against the SUT in an isolated environment,
a deterministic grep layer checks facts before a judge subagent (running on a
different model) issues verdicts, and reports go back to the human. Browser
acceptances (v0.6.0) add a visual layer: state screenshots next to transcripts,
a visual-reviewer subagent marks flaws with severity frames — the judge never
sees that markup and verdicts do not change.

Docs: `README.md` (RU, canonical) with EN/ZH/ES/FR translations (`README.en.md`
and siblings) · `docs/spec.md` · `docs/architecture.md` (+ interactive
`docs/architecture.html`).

## Layout

- `skills/acceptance-test/SKILL.md` — orchestrator instructions, five phases A–E
- `agents/` — role definitions: analyst, role-user (executor), judge,
  visual-reviewer (marks browser screenshots; judge-blind by design)
- `knowledge/` — taxonomy (5 card types), adapters and environment isolation,
  oracle (verdict scale), sandbox levels, golden control sets
- `scripts/` — deterministic machinery: `run-cards.sh` (headless runs),
  `parse-events.py`, `check-facts.py` (fact grep before the judge),
  `judge-batch.py` / `judge-control.py`, `sandbox.py` + `sandbox-proxy.py`
  (docker isolation, fail-closed), `sec-checks.py`, `annotate-visuals.py`
  (validates visual markup, builds the visual review page, publishes named
  samples)
- `runs/` — acceptance artifacts (cards, transcripts, facts, verdicts, reports).
  Case policy: third-party runs are published only with the owner's consent —
  ask before committing any.
- `examples/evil-plugin` — deliberately malicious plugin used by security checks;
  run it only inside the docker sandbox.
- `tests/` — unit tests and live proxy tests.

## Commands

- Unit tests: `python -m unittest tests.test_scripts -v`
- Live proxy tests (dummy key, no LLM calls): `python -m unittest tests.test_proxy_live -v`
- Security suite: `python scripts/sec-checks.py docker --out runs/sec-ci`
- CI (`.github/workflows/security.yml`) runs the above on ubuntu. FAIL or ERROR
  fails the pipeline; SKIP is not PASS.

## Conventions

- Working language for docs and commits: Russian. RU README is canonical; keep
  the EN/ZH/ES/FR translations in sync when changing it.
- Verdict scales are fixed — never invent new statuses:
  judge: GOT / HONEST / PARTIAL / FAIL / ATTACK_PASSED / INVALID;
  det layer: DET_OK / DET_MISSING / DET_LEAK / DET_NA / DET_NO_DATA.
- Frontmatter descriptions must parse as strict YAML: wrap values containing
  colons in double quotes (Claude Code is lenient, external tools like APM
  are not).
- docs/benchmarks.md (acceptance log) is generated by
  `python scripts/build-benchmarks.py`; never hand-edit it. A new run needs a
  `bench.yaml` sidecar (sut/type/adapter/env/findings); counts and cost come
  from index.jsonl and cost.md. The generator refuses to write the page if its
  guard filter finds private markers — run `--selftest` for the positive control.
  Private runs stay in the private twin repo only.
- Oracles are written before the run and are never edited after it. Do not
  "fix" a card's expectations to match observed answers.
- Never print or commit secrets (gateway keys, tokens). The real LLM key lives
  only in the sandbox proxy environment.
- Commit identity: this repo publishes under the public identity
  `vonavikon <workwithkonstantin@gmail.com>` only. Before committing, check
  `git config user.email`; if it shows any other address (for example a
  corporate one picked up from another environment), switch:
  `git config user.name vonavikon && git config user.email workwithkonstantin@gmail.com`.
  Commit messages must not mention employer names or internal project names.
- Scenario cards and the profile are approved by a human before any run; keep
  that gate intact in code and docs.

## Before you finish

Run the unit tests; if you touched sandbox or proxy code, run the security
suite. Keep public commits free of private run data.
