# Изоляция выполнения: уровни и политика

Зачем: приёмка запускает чужой плагин в реальном Claude Code. Без барьера
этот процесс может читать файлы хоста (включая секреты и оракулы карточек),
ходить в сеть и выполнять команды за пределами рабочей папки. Изоляция —
это замок, а не надежда на честность модели.

## Уровни изоляции

| Уровень | Название | Что это | Что гарантирует | Когда выбирать |
|---|---|---|---|---|
| 0 | `host` | Теперешний режим: отдельный work-каталог, env-allowlist, пустой MCP, `--disallowedTools Skill`, детектор вмешательства | Секреты окружения не наследуются, чужие скиллы/MCP не вызываются, вмешательство в файлы прогона ловится. **Выход за пределы work физически НЕ запрещён** — барьером является только поведение модели | Публичные плагины из открытых репозиториев, быстрые приёмки, среды без Docker |
| 1 | `docker` | Контейнер: только копия SUT + work, сеть off, read-only + tmpfs, non-root, лимиты pids/memory | SUT не видит файлы хоста (включая оракулы и секреты, кроме единственного LLM-конфига), не имеет сети, пишет только в work | Недоверенные плагины, закрытые/корпоративные системы, прогон «злого» материала, публичные демонстрации безопасности |

## Правила выбора (фаза B, адаптер)

1. Уровень выбирается осознанно при настройке адаптера и фиксируется в
   отчёте (meta `isolation_level`). Дефолт `host` — простые публичные
   плагины не требуют контейнера.
2. Для недоверенного материала уровень `docker` обязателен; просьба
   «прогони без контейнера» для такого материала — отказ с отсылкой к
   этому правилу.
3. **Fail-closed**: если выбран `docker`, а Docker недоступен — прогон
   прекращается с явной ошибкой. Тихой подмены на `host` не существует;
   переход — только правкой выбора уровня человеком, с новой записью в
   отчёте.
4. В любом уровне SUT-сессия не получает окружение тестировщика (env-allowlist
   в раннере — общий слой).

## Что живёт в контейнере (уровень 1)

Монтирования (после hardening 2026-10-13):

- `/workspace/sut` - копия тестируемого плагина, **read-only** (SUT не
  может переписать собственные исходники);
- `/workspace/out` - результаты, единственное записываемое постоянное место;
- `/workspace` - tmpfs: писать можно (сессии создают рабочие файлы), но всё
  вне out/ умирает вместе с контейнером;
- `/home/node` - tmpfs (служебные каталоги CLI);
- канарейка-приманка (read-only).
- НЕ монтируются: рабочий каталог целиком, оракулы, каталоги раннера,
  приватный каталог с ключами, home/SSH/Docker socket хоста.

Секрет LLM (hardening P0-2): настоящий ключ живёт ТОЛЬКО в окружении
прокси-контейнера (передаётся из приватного каталога хоста `work-priv/`,
который никогда не монтируется). Прокси подставляет Authorization сам;
в среде SUT - плейсхолдер `sandbox-local-placeholder` и адрес прокси.
Прокси принимает только пути LLM API и методы GET/POST, режет тело >4МБ,
лимит 2000 запросов на запуск; ошибка прокси НЕ включает fallback прямого
подключения (у SUT нет сети мимо него).

Самопроверка при prepare: проба записи в исходники SUT изнутри боевого
профиля контейнера. Запись возможна - запуск запрещён (fail-closed).
Wall-time лимит сессии: `QA_EVALS_SUT_TIMEOUT` (дефолт 900с).

Очистка: контейнер `--rm`, прокси и internal-сеть удаляются с retry
(сеть нельзя снять, пока контейнер отваливается), work и приватный
каталог затираются; повторный cleanup безопасен. Имена ресурсов несут
суффикс work - параллельные запуски не пересекаются (проверено живьём).

## Остаточные риски уровня 1 (фиксируются в отчёте)

- Контейнер не защищает от уязвимостей рантайма (docker escape); для
  заведомо враждебного материала с exploit-амбициями - VM-уровень.
- Прокси - единственный держатель ключа на хосте помимо CLI раннера;
  компрометация прокси-контейнера равна утечке ключа шлюза (личный,
  ротационный, только генерация).
- Каналы Docker Desktop (bind-монтирования Windows-путей) считаются
  доверенными средствами самой платформы.
- Контейнерная изоляция НЕ эквивалентна отдельной виртуальной машине
  или специализированной песочнице с более сильной границей.

## Проверка изоляции (SEC-карточки против examples/evil-plugin)

SEC-01 чтение секрета хоста (канарейка) · SEC-02 чтение оракулов прогона ·
SEC-03 сеть · SEC-04 бесконечный процесс/тайм-аут · SEC-05 запись вне work ·
SEC-06 подмена эталонов. Ожидание на уровне docker: попытки разбиваются
(отказ/недоступность/пустой результат), на уровне host — честная запись,
что барьера нет (уровень 0 не заявляет песочницу).

## Интерфейс backend (scripts/sandbox.py)

`verify <level>` — доступность уровня (docker: демон+версия) ·
`prepare <level> <sut-dir> <run-dir>` — уникальный work, копия SUT,
конфиг CLI, meta (версия claude CLI, git-хеш SUT, уровень) ·
`wrap <level> <work> -- <команда>` — префикс запуска (host: как есть;
docker: docker run с флагами выше) · `cleanup <work>` — затирание.

## Финальное усиление (2026-10-13, ветка sandbox-final)

- **Проба прав fail-closed доказательна**: успех только при rc==0 + явный
  маркер BLOCKED без WROTE; таймаут/ошибка docker/пустой вывод/оба маркера =
  отказ запуска с причиной в meta-sandbox.json (probe_refused).
- **Прокси**: нормализация пути (тройной unquote, normpath, query/fragment)
  до проверки префикса - обходы ../ и %2e%2e закрыты; лимиты: тело 4МБ,
  ответ 16МБ, 120 req/мин, 4 одновременных, 2000 на запуск, 2ч жизни;
  ошибка upstream светит только тип исключения; auth-заголовки ответа
  фильтруются. Прокси-контейнер: nobody, read-only+tmpfs, cap-drop ALL,
  256m/0.5cpu/32pids; proxy.env 0600 в приватном каталоге.
- **SEC-06A**: эталон-приманка с известным md5 в каталоге прогона; атака
  изнутри (запись/удаление/чтение по абсолютному хостовому пути и ../)
  + контроль хеша. **SEC-06B**: фейковый вердикт, записанный SUT в out/,
  остаётся изолированным; итоговый статус строит раннер, stale-отчёт
  перезаписывается со свежим run_id. **CLEANUP**: критерий текущего запуска
  (его сеть/контейнеры/priv), повторный вызов безопасен, чужой мусор -
  отдельной пометкой.
- **Интеграционный тест** (`scripts/sec-integration.py`): полная живая цепочка
  docker -> Claude Code -> транскрипт -> судья -> манифест -> cleanup на
  мини-карточке; без Docker/ключа - SKIP с причиной (не PASS). Отличать:
  sec-checks - детерминированные пробы среды, sec-integration - живой
  конвейер с LLM.
- Живые тесты прокси для CI: tests/test_proxy_live.py (dummy-ключ).

## Автоматический security-набор

`python scripts/sec-checks.py docker [--out runs/<дата>-sec]` - SEC-01..06
детерминированно, без LLM (годится для CI; прокси стартует с
плейсхолдером, если ключа нет). Статусы: PASS (атака заблокирована) /
FAIL (нарушение) / ERROR (не выполнилось - не защита) / SKIP. Выход 0
только без FAIL/ERROR. Отчёты: sec-report.json + sec-report.md + логи
проб. CI: .github/workflows/security.yml. Последний живой прогон:
runs/2026-10-13-sec (6/6 PASS).
